# Proofs

A native fast path in the runtime — a *jet*: recognize a known tree applied to an argument, and
compute the answer in C++ instead of reducing — is only as good as the claim that it computes
what the tree does. This is the machinery to make that claim a theorem, in Lean 4 with nothing
but its core library:

```
lake build        # from here; about 23 s from clean, nearly all of it the kernel checks below
```

`lean-toolchain` pins `leanprover/lean4:v4.34.1`. There is no `sorry`, and every theorem below
rests on the standard axioms (`propext`, `Classical.choice`, `Quot.sound`) or fewer — in
particular not on `Lean.ofReduceBool`: the jets are checked with `decide +kernel`, never
`native_decide`, so Lean's compiler is not trusted. To see for yourself:

```
echo 'import TreeCalculus
#print axioms TreeCalculus.Jets.skipLine_spec' | lake env lean --stdin
```

## What is proven

The machine (`Run a b r`: `apply(a, b)` returns `r`) is deterministic and computes exactly what
the reduction rules do. The runtime around it — the machine plus a memo it may hit, fill and
forget any way at all, plus jets: any relation `J` on states every transition of which is a
composite of real steps — returns what the machine does:

```lean
theorem Run.det (h : Run a b r) (h' : Run a b r') : r = r'
theorem run_iff_eval : Run a b r ↔ Eval a b r
theorem runtime_sound (hj : ∀ s t, J s t → Reaches s t) (hm : m.Sound)
    (h : Star (RStep J) ⟨.reduce a b [], [], m⟩ ⟨.dispatch r [], [], m'⟩) :
    Run a b r ∧ m'.Sound
```

Every step the symbolic machine takes is the concrete machine's on every instance:

```lean
theorem sstep_next {s : State STree} (h : sstep s = .next s') (σ : Nat → Tree) :
    step (s.map (subst σ)) = some (s'.map (subst σ))
```

The checkers are sound — each `check … = true` is a closed `Bool`, and says something about
every argument, of any shape:

```lean
theorem checkRun_sound (h : checkRun F x r n = true) : Run F x r

theorem checkMember_sound (h : checkMember P ks n = true) (c : Tree) :
    Run P c (if c ∈ ks then .true else .false)
theorem checkMember_single (h : checkMember P [k] n = true) (c : Tree) :
    Run P c (if c = k then .true else .false)

theorem checkDropThrough_list (h : checkDropThrough F ks n = true) (hxs : IsList xs) :
    Run F xs (dropThrough ks xs)
theorem checkDropThrough_skip (h : checkDropThrough F ks n = true) (hc : c ∉ ks)
    (ht : Run F t r) : Run F (.fork c t) r
theorem checkDropThrough_hit (h : checkDropThrough F ks n = true) (hk : k ∈ ks) (t : Tree) :
    Run F (.fork k t) t
```

and license the transitions a runtime takes for the jet — the `J` of `runtime_sound`:

```lean
inductive MemberJet (P : Tree) (ks : List Tree) : State Tree → State Tree → Prop
  | answer : MemberJet P ks (.reduce P c k) (.dispatch (if c ∈ ks then .true else .false) k)
inductive DropJet (F : Tree) (ks : List Tree) : State Tree → State Tree → Prop
  | skip : c ∉ ks → DropJet F ks (.reduce F (.fork c t) k) (.reduce F t k)
  | hit : c ∈ ks → DropJet F ks (.reduce F (.fork c t) k) (.dispatch t k)
  | nil : DropJet F ks (.reduce F .leaf k) (.dispatch .leaf k)

theorem MemberJet.reaches (h : checkMember P ks n = true) : MemberJet P ks s t → Reaches s t
theorem DropJet.reaches (h : checkDropThrough F ks n = true) : DropJet F ks s t → Reaches s t
```

`checkMember` is a predicate on characters — or on any trees — as a finite set: `equal_const k`
is `[k]` (`checkMember_single`), `Char.is_newline` is newline and carriage return. Every tree
`c` is covered, whatever its shape, not only the ones that encode a character.

`dropThrough ks` drops a list's elements up to and including the first one in `ks`; `IsList`
constrains only the spine, so the elements are arbitrary trees. `ks` is a list because loops
differ in where a line ends: the compiler's `skip_line` stops at a newline only, its
`_skip_comment` at a newline *or* a carriage return. `skip` is what lets a native loop give up
anywhere: skip what it likes, then hand the rest back to the tree.

Applied to trees the toolchain produced (`Jets.lean`; lambada 7efbcd1, see `jets/gen.mjs`):

```lean
theorem eqConstNewline_spec (c : Tree) :
    Run eqConstNewline c (if c = newline then .true else .false)   -- `equal_const 10`
theorem isHash_spec (c : Tree) :
    Run isHash c (if c = hash then .true else .false)              -- the compiler's `_is_hash`
theorem isNewline_spec (c : Tree) :                                -- `Char.is_newline`
    Run isNewline c (if c ∈ [newline, carriageReturn] then .true else .false)
theorem skipLineFix_spec (h : IsList xs) :
    Run skipLineFix xs (dropThrough [newline] xs)                  -- a loop written with `fix`
theorem skipLine_spec (h : IsList xs) :
    Run skipLine xs (dropThrough [newline] xs)                     -- the compiler's `skip_line`
theorem skipLine_skip (hc : c ∉ [newline]) (ht : Run skipLine t r) :
    Run skipLine (.fork c t) r
theorem skipLine_hit (t : Tree) : Run skipLine (.fork newline t) t
theorem skipComment_spec (h : IsList xs) :
    Run skipComment xs (dropThrough [newline, carriageReturn] xs)  -- the compiler's `_skip_comment`

/-- The compiler's jets (skipLine, skipComment, isNewline, isHash), as transitions. -/
theorem compilerJets_sound (hm : m.Sound)
    (h : Star (RStep compilerJets) ⟨.reduce a b [], [], m⟩ ⟨.dispatch r [], [], m'⟩) :
    Run a b r ∧ m'.Sound
```

and the checkers refuse what is false — among them `checkDropThrough skipComment [newline]`
(a carriage return ends a comment too) and `checkDropThrough skipLine [newline,
carriageReturn]` (to `skip_line`, a carriage return is a character like any other).

## Which loop a source's comments cost

A jet pays where the reductions are. `compile_file` on forest's
`src/type/system/simple/paper_experiments/main.lamb` (5 MB: three ~1.7 MB `# = …` lines, 1,055
bytes of code) spends nearly all of them on lines that are not code, and where depends on the
compiler:

- **Base (lambada 6ef3de4).** `statements` splits the source into lines (`List.split_on 10`)
  and keeps those `_is_code_line` accepts, so every line is built a character at a time for one
  character of it to be looked at. That is no drop-through — it builds what it reads — and no
  checker here fits it. `_skip_comment` is not on that path: the tokenizer reaches it only for a
  comment inside a statement. A native `DropJet` on it fires twice on this source and skips 74
  characters (47,612,116 steps → 47,611,035).
- **Rewritten (lambada 7efbcd1, the compiler-tree track's).** `statements` reads every line past
  its first character with `skip_line` — a comment or a result whole, a code line before its
  text is copied out — a drop-through through newline: `skipLine` above. A native `DropJet` on
  it takes 3,161,664 characters in 64 calls, and the reduction falls from 6,475,725 steps
  (0.65 s) to 151,342 (0.024 s) — fewer than without the jet on the source with its comment and
  blank lines taken out (152,857). On `…/termination/paper_experiments/main.lamb` (1.2 MB):
  787,567 characters in 65 calls, 1,728,420 steps → 152,578.

The output is the same byte for byte in every one of these runs, base's included (sha256
`92c528b6bcf22b16…` and `02cc0e491860404e…`). They are `runner -s` (eager), with step 4's loop
below patched into `apply` for the measurement, keyed on the loaded `compile_file.dag`'s index
for the symbol; putting a jet into the runtime is not part of this directory.

## The machine, rule by rule

`apply(a, b)` in [`eager-graph-nil-mmap-32.hpp`](../implementation/cpp/eager-graph-nil-mmap-32.hpp)
is a loop over two labels with its continuations on a heap stack; `step` is one `goto` of it:

| C++ (`apply`) | Lean (`step`) |
| --- | --- |
| `reduce:` with `a`, `b`, and the frames above `base` | `State.reduce a b k` |
| `dispatch:` with `result` | `State.dispatch r k` |
| `APPLY_TO(arg)`, `COMPUTE_AND_APPLY(fn, arg)` | `Frame.applyTo arg`, `Frame.computeAndApply fn arg` |
| `if (!an.u)` — `apply(△, b) = △b` | `.reduce .leaf b k ↦ .dispatch (.stem b) k` |
| `if (!an.v)` — `apply(△u, b) = △ub` | `.reduce (.stem u) b k ↦ .dispatch (.fork u b) k` |
| `if (!un.u)` — `apply(△△y, b) = y` | `.reduce (.fork .leaf y) _ k ↦ .dispatch y k` |
| `if (!un.v)` — push `COMPUTE_AND_APPLY(un.u, b)`, `a = y` | `.reduce (.fork (.stem u') y) b k ↦ .reduce y b (.computeAndApply u' b :: k)` |
| `if (!bn.u)` — `b = △: w` | `.reduce (.fork (.fork w _) _) .leaf k ↦ .dispatch w k` |
| `if (!bn.v)` — `b = △d: apply(x, d)` | `… (.stem d) k ↦ .reduce x d k` |
| `b = △de` — push `APPLY_TO(e)`, `a = y; b = d` | `… (.fork d e) k ↦ .reduce y d (.applyTo e :: k)` |
| pop `APPLY_TO`: `a = result; b = f.arg1` | `.dispatch r (.applyTo e :: k) ↦ .reduce r e k` |
| pop `COMPUTE_AND_APPLY`: push `APPLY_TO(result)`, `a = f.arg1; b = f.arg2` | `.dispatch r (.computeAndApply f e :: k) ↦ .reduce f e (.applyTo r :: k)` |
| `_stack.size() == base`: `return result` | `.dispatch _ [] ↦ none` |

`Run a b r` is one call returning `r`: `reduce a b []` reaches `dispatch r []`.

Left out, and why it changes no result:

- **`MEMOIZE` frames and the memo.** `Runtime.lean` puts them back: `RStep` may, besides every
  rule, on any `reduce a b` hit an entry (`memo_get`), push `MEMOIZE(a, b)` under what the rule
  pushes, `memo_put` when that frame pops, and forget any entries at any time — which is every
  admission and eviction policy at once (the direct-mapped overwrite, `MEMO_MIN_STEPS`, a
  collection's filter). `runtime_sound`: started with sound entries, it returns what `Run` says
  and leaves only sound entries. The reason is `Run.frame` — a run is oblivious to the stack
  under it, so a hit is a composite of real steps — and the frames above a `MEMOIZE(a, b)` being
  exactly what `reduce a b` pushed, so what it records is `Run a b r`. Jets ride on the same
  argument: a transition that is a composite of real steps is as good as the steps.
- **Hash-consing.** The memo is keyed by node indices, the machine by trees. They agree because
  interning is exact: equal trees are equal indices and vice versa.
- **Collection.** It frees only what no root, frame or operand reaches, moves nothing, and drops
  every memo entry one of whose three nodes it frees, so no index is reused under a stale entry.

## What is trusted

- That `step` is `apply`'s loop: the table above, which is the whole of it. (`run_iff_eval` ties
  `step` to the reduction rules every implementation in this repository is tested against.)
- Exact hash-consing, and a collector that frees nothing reachable and filters the memo.
- That a jet's native code takes only transitions of its relation (`MemberJet`, `DropJet`) —
  answers with the set membership it was checked for, skips only elements that are no
  separator — and fires on exactly the tree the theorem is about: its index, interned from the
  same `jets/*.dag` the Lean definition was generated from.
- Lean's kernel.

Not trusted: `dag2lean.mjs` (a wrong translation is a theorem about some other tree, which the
point above already excludes), and everything in `Symbolic.lean`, `Check.lean` and
`Runtime.lean`, which is proven.

## How a checker works

`explore` runs the machine on the jet's tree applied to an argument with variables — `var 1`,
the part the jet inspects, and for loops `var 0`, the tail it hands on. When a rule depends on a
variable's shape it splits the branch three ways (leaf, stem, fork, over fresh variables) and
records the refinement in `var 1`'s pattern; `var 0` is never split, so a branch that looks at
the tail fails. A checker is only a `Verdict`: which states end a branch, and what they need of
the pattern. `checkDropThrough` ends a branch at the tail call `reduce F (var 0)` with an empty
stack — accepted if no separator fits the pattern — or at `dispatch (var 0)` — accepted if the
pattern is pinned to one of the separators; `checkMember` at `dispatch v`, accepting `v = true`
if the pattern is pinned to one of `ks` and `v = false` if none of them can fit it.
`explore_sound` turns acceptance into `Inv` for a set of branches covering every instance, and
each checker's theorem reads its statement off those.

**Sharing.** A runtime tree is a DAG whose expansion can be far larger (`_skip_comment`: 84
distinct nodes, 16,284 as a tree). `dag2lean.mjs` writes one definition per distinct node, so the
Lean term is the DAG. `STree.lit t` embeds a concrete tree without walking it: `view` exposes one
level, and substitution, instantiation and `maxVar` stop at a `lit`. What remains is comparing
trees (`fits`, e.g. recognizing the tail call's function as `F`), and that the kernel does in time
proportional to the DAG, because it caches every `whnf` it computes, keyed by term: the recursive
comparison of a shared pair of nodes is the same term every time it recurs. `Tests.lean` pins
that down on trees laid out as `dag2lean.mjs` lays them out, one definition a node: two separately
defined trees of 2^60 leaves are equal, and one of them differs from a third only in its last
leaf, each checked in about 11 ms.

**Cost.** The kernel evaluates at roughly 250 µs per symbolic step (30,134 concrete steps took
7.5–8.2 s); a bare countdown loop costs it 37 µs an iteration, so that is interpretation
overhead rather than anything in the checker. Measured with
`lake env lean -Dprofiler=true -Dprofiler.threshold=1 TreeCalculus/Jets.lean`:

| Jet | Distinct nodes | Branches | Symbolic steps | Kernel check |
| --- | ---: | ---: | ---: | ---: |
| `eqConstNewline` (`equal_const 10`) | 34 | 23 | 163 | 0.06–0.12 s |
| `isHash` (compiler) | 48 | 33 | 241 | 0.10–0.27 s |
| `isNewline` (`Char.is_newline`) | 65 | 43 | 786 | 0.21–0.30 s |
| `skipLineFix` | 82 | 23 | 420 | 0.14–0.16 s |
| `skipLine` (compiler) | 57 | 23 | 886 | 0.19–0.39 s |
| `skipComment` (compiler) | 84 | 507 | 33,434 | 12.0–13.1 s |

The ranges are repeated runs on a shared machine.

`_skip_comment` explores a table over the character's low 6 bits (`Memo.precompute_alt
Memo.gen_ascii_low`), and every shape a tree could take at each bit, so it has many branches.

## Adding a jet

1. Add the tree to `jets/gen.mjs` — a LambAda expression, or a symbol of `compile_file.dag` —
   and run it (`LAMBADA=<lambada checkout> node jets/gen.mjs`). It builds the eager runner from
   this repository's `runner.cpp`, writes the normal form to `jets/<name>.dag`, and regenerates
   `Jets/Trees.lean` from all of them.
2. If a checker has the jet's shape, the jet is one line in `Jets.lean`:
   `theorem <name>_check : checkDropThrough <tree> [<separators>] 1000 = true := by decide +kernel`,
   and its specification follows from the checker's theorems; add its relation to
   `compilerJets`. The number is fuel — the longest branch it may take, in steps and splits; a
   check that runs out fails rather than lies.
3. If none has, write one: a `Verdict` saying which states end a branch and what they need of the
   pattern, its soundness theorem from `explore_sound` (the way `checkMember_sound` reads its
   own off it, about 15 lines), and the relation of transitions it licenses.
4. Implement the native path keyed on the tree's index, taking only those transitions, and cite
   the theorem that licenses them. For a `DropJet`, at `reduce:` in `apply` — `F` and the
   separators interned from the same trees and held as roots, so an index comparison is a tree
   comparison:

   ```cpp
   if (a == F) for (;;) {                                     // DropJet: Check.lean
     const Node xn = _arena[b];
     if (!xn.u) { result = b; goto dispatch; }                // nil
     if (!xn.v) break;                                        // a stem: the tree's to answer
     if (xn.u == k) { result = xn.v; goto dispatch; }         // hit (xn.u ∈ ks)
     b = xn.v;                                                // skip (xn.u ∉ ks)
   }
   ```
